# 生理变化与对话时间轴 · 候选方案

日期：2026-10-25。状态：用户已明确暂缓，不进入当前开发计划。保留官方资料研究，未实现、未启用 HealthKit、未读取用户健康数据。Alaud 0.2 的录音、存储与授权保持不变。

## 目标与判断边界

把可用的心率样本与同期对话关联，帮助本人回看、确认哪些话题值得关注。界面称为「值得回看的时刻」，不生成确定的情绪评分或重要性结论。

心率变化、情绪和话题的重要性不是一一对应关系，时间上的同现也不能证明某句话导致变化。说话、活动与测量误差需要考虑；生理反应和采样存在时间不确定性。缺少说话人辨识时，只能称「同期对话」，不能断言用户当时正在听。Agent 输出候选关联和证据，后续用用户确认改进，不能据此直接执行工作或替用户决策。

## 已核实的能力与限制

| 项目 | 结论 |
| --- | --- |
| 普通会议心率 | 可经授权读取 HealthKit 中已经产生的样本；录音后台会话不等于开启高频心率传感器。目标用户设备为 Series 11，不能套用新型号的连续采样说明。实际密度、延迟及缺口仍需实测。 |
| 强制高频采样 | Apple DTS 明确表示，除了活跃的 HKWorkoutSession，没有可触发高频心率采样的 API。启动 workout 会影响活动圆环；不以虚构运动换取会议心率。 |
| 呼吸率 | Apple Watch 官方能力主要为睡眠期间的呼吸率，不能承诺清醒会议有连续数据；首轮排除。 |
| HRV 与压力/情绪 | 不承诺连续 HRV，也不把单一生理量直接转换成情绪类别。 |
| 功耗 | 首轮只读取既有样本，不新增高频采样；真实耗电与录音兼容性尚未测试。 |

## 建议的首轮验证

1. 在用户明确启用后，仅在 iPhone 请求读取心率；拒绝授权或没有样本均可正常录音。查询限定到所选会议的时间范围，展示来源和样本实际时间，等待健康数据同步后可重新查询。
2. 先做一段 20–30 分钟无敏感内容的真实录音验证。脱离 Xcode 调试器，测试熄屏、回表盘以及暂停/恢复；记录样本数、采样间隔、最长缺口、到达延迟与电量。没有实测前不承诺能定位秒级反应。
3. 使用 UTC 时间把样本对齐到实际录音区间。当前转写 offset 是累计音频时间，暂停/中断有 gaps；不能简单用「健康时间减会议开始」定位原文。需要验证首帧时间、缺口及系统时间变化，无法可靠映射的区间显示未知。
4. 图上保留样本点与空白，不把数分钟的缺口画成可信的连续曲线。样本足够时才比较本场局部基线并提出回看片段；不把相邻稀疏样本之差标成突然变化。窗口按采样密度调整，保留上下文而非武断归因到一句话。
5. 候选卡片包含时间区间、观测变化、数据覆盖、同期对话及一键回听。本人可确认有关/无关，补充紧张、兴奋、专注等体验。先验证是否帮助找到有价值片段，再决定是否研究更高时间分辨率的采集方案。

## 存储和 Agent 边界

Apple App Review 5.1.3(ii) 明确限制第三方 App 把个人健康信息存到 iCloud。Apple 自身健康数据同步和第三方 App 将导出的健康数据写入自己的 Drive/CloudKit 容器不是同一条路径。因此不把心率、健康样本 ID、健康派生片段标记或推断塞进现有 meeting.json、云端快照、备注或默认 Markdown/JSON 导出。

建议首轮在 iPhone 本地临时组合 HealthKit 样本与录音时间轴，优先不复制原始健康库；确需保存的健康关联与确认另用有文件保护、排除云备份的本地存储。录音继续使用既有 iCloud 方案，Mac 首轮只共享普通录音库，不默认同步健康层。

Agent 接入位置尚未定义。本地处理与第三方 AI 外发要分别设计；明确具体健康字段、接收方、用途和保留方式后才能请求外发同意。授权不自动解决 HealthKit 用途限制：按 5.1.2 / 5.1.3，健康管理以外的数据挖掘及第三方用途还需单独核实，不能把个人偏好推断默认当成已允许的用途。健康推断同样不自动混入通用云端会议资料。
